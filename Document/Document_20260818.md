# WindScore 设计文档

> 本文首先用于统一 WindScore 的产品目标、核心理念和行为边界，帮助产品、设计、工程以及 LLM 理解我们正在做什么、明确不做什么。
>
> 本文不是 MVP 技术实现方案，也不规定完整的算法、数据表结构或界面细节。具体实现将由后续的 MVP 实现路线、分析规则和数据设计文档补充。

## 1. 产品定位

> **WindScore 是一个面向 Solo 钢琴演奏者的长期练习仪表盘。它基于乐谱、MIDI 演奏记录、练习行为和用户反馈，帮助用户看见自己在不同条件下能够稳定完成什么，以及这些可观察的控制能力如何随着练习发生变化。**

WindScore 不是：

- AI 钢琴老师；
- 专业演奏评分器；
- 演奏比赛裁判；
- 音乐审美评价器；
- 参考大师演奏的模仿系统。

WindScore 不要求用户更像李斯特、郎朗或任何参考演奏者。

它的目标是帮助用户：

- 更快发现容易卡住的位置；
- 减少“练了很久却感觉没有进步”的挫败；
- 找到自己目前能够稳定控制的速度和练习条件；
- 了解自己在有提示和无提示条件下的完成表现；
- 保留个人速度、力度、呼吸和演奏风格；
- 通过长期数据看见自己原本难以察觉的变化。

WindScore 不回答：

> **“你弹得好不好？”**

而是回答：

> **“你最近练了什么？在什么条件下能够做到什么？哪些地方正在变得更容易控制？”**

---

# 2. 核心产品哲学

## 2.1 不评价音乐人格

系统不判断：

- 是否有天赋；
- 是否有音乐性；
- 是否有“灵魂”；
- 风格是否高级；
- 是否像专业演奏者；
- 是否像某位大师；
- 是否应该采用某种审美。

这些属于音乐表达与个人判断，不属于 WindScore 可以可靠客观测量的范围。

系统只描述：

> 可观察事实、历史变化和用户自己确认过的意义。

---

## 2.2 不把乐谱或参考 MIDI 当成唯一正确答案

MusicXML 和参考 MIDI 为系统提供可计算的结构参考，但不构成唯一演奏答案。

MusicXML 主要提供：

- 音高；
- 时值；
- 节拍位置；
- 小节结构；
- 声部；
- 谱表；
- 乐谱中的明确记号。

参考 MIDI 可以提供：

- 可播放的时间结构；
- 音符事件序列；
- 练习定位和同步参考。

但它不代表用户必须复制：

- 参考速度；
- 力度；
- rubato；
- 踏板；
- 呼吸；
- 表达方式；
- 参考演奏者的风格。

以下情况不应自动判定为错误：

- 用户选择较慢或较快的速度；
- 合理的速度变化；
- rubato；
- 自由呼吸；
- 个性化力度；
- 不同踏板方式；
- 改编、简化或个人化的演奏方式。

系统需要区分：

```text
实际音高是否与当前乐谱的预期音符匹配
```

和：

```text
演奏是否具有个人表达
```

前者可以进行有限的技术分析，后者不属于系统评分范围。

---

## 2.3 不把一次演奏当成能力结论

一次演奏只能说明：

> 这一次发生了什么。

它不能直接证明：

> 用户的某项能力是什么水平。

只有在相近条件下积累多次练习记录后，系统才可以描述某个行为是否呈现稳定趋势。

例如：

```text
单次事实：
第 11 小节出现一次 1.5 秒停顿。

重复观察：
第 11 小节最近 5 次尝试中有 3 次出现类似停顿。

候选趋势：
这个位置可能仍然比较难稳定完成。
```

系统不应该直接输出：

```text
你的节奏能力较弱。
你还没有掌握这首曲子。
你的读谱能力正在提升。
```

WindScore 描述的是数据中的变化，而不是给用户贴长期能力标签。

---

## 2.4 记录可控制性，而不是评判能力

WindScore 关注：

```text
在什么条件下
用户能够完成什么
出现了什么可观察偏差
最近是否变得更容易控制
```

系统可以记录：

- 能否完成某个片段；
- 能否连续完成；
- 能否在某个速度范围内完成；
- 有提示和无提示时的表现差异；
- 是否容易中断；
- 漏音或错音是否减少；
- 是否能够保持用户自己的演奏方式。

系统不应直接将这些信息转换为：

```text
钢琴水平
音乐天赋
专业程度
艺术表现力分数
```

---

## 2.5 分析结论必须具有证据等级

系统中的不同结论，不应被当作同等可靠。

WindScore 必须区分：

```text
发生了什么
系统观察到什么
长期可能说明什么
用户如何理解这件事
```

因此，每条系统分析结论都应具有：

- 证据等级；
- 可信度；
- 证据来源；
- 分析版本。

用户确认的意义不属于更高一级的系统证据。它是与证据等级并列的用户语义，用来说明用户如何理解某个观察，以及该观察是否应参与后续趋势分析。

---

# 3. 证据等级模型

## 3.1 Level 1：Fact，记录事实

这是最接近原始数据的一层。

示例：

```text
在 12.43 秒处未检测到对应的 MIDI Note On。
在第 11 小节附近检测到 1.5 秒的无按键区间。
本次演奏到达了第 16 小节。
用户在 18:05 开启了键盘提示。
```

Fact 的特点：

- 来源明确；
- 可从原始数据重新计算；
- 不包含能力或价值判断；
- 通常不需要历史比较。

Fact 也不代表设备绝对没有误差。更准确的表达是：

> 根据当前 MIDI 记录，系统未检测到对应事件。

而不是：

> 用户一定漏弹了这个音。

当设备状态、乐谱对齐或事件识别不足以支持可靠描述时，系统应明确保留：

```text
无法可靠判断
```

“暂不判断”是合法结果，不应为了生成反馈而强行解释。

---

## 3.2 Level 2：Observation，较可靠的重复观察

Observation 是基于多个 Fact 提取出的可重复模式。

示例：

```text
最近 5 次相近条件的尝试中，
第 10–12 小节有 3 次出现类似的停顿。
```

或：

```text
最近 4 次在相近速度下的练习中，
该片段均完成到第 16 小节。
```

Observation 的特点：

- 来自多个事实；
- 有明确的时间范围和样本数量；
- 通常需要满足相近条件；
- 仍然不直接等同于能力结论。

---

## 3.3 Level 3：Candidate Trend，候选趋势

Candidate Trend 是系统根据历史观察提出的保守解释。

示例：

```text
这个位置可能仍然比较难稳定完成。
第 11 小节附近的中断可能正在减少。
在无提示条件下，这段可能比之前更容易完成。
```

Candidate Trend 必须使用保守语言：

```text
可能
似乎
目前数据显示
在相近条件下
暂时观察到
```

不能直接写成：

```text
你已经掌握了这里。
你的能力提高了。
你已经不需要提示。
```

Candidate Trend 应允许用户在查看一段时间的聚合结果后：

- 确认这个模式值得关注；
- 忽略或排除这个模式；
- 标记为有意行为、自由演奏或设备异常；
- 修改问题区域；
- 选择是否纳入未来比较。

系统不要求用户为每一次停顿、错音或未匹配事件逐条解释。用户确认的是一段时间内反复出现的模式，而不是某个原始事件的“正确原因”。

---

## 3.4 User-Confirmed Meaning，用户确认的意义

用户反馈不改变原始事实，也不构成更高等级的客观证据。它为一段时间内形成的观察或趋势增加个人语义，并影响后续是否纳入趋势分析。

用户确认的对象主要是聚合后的模式，而不是单次事件。例如：

```text
系统观察：
最近一个月的大多数位置都能够连续完成，
但第 14 小节附近几乎每次都会出现相似的停顿。

用户反馈：
这是我有意留下的呼吸。

系统处理：
保留所有原始事实和观察，
将该区域标记为 intentional，
后续不再把它作为“卡顿”参与默认趋势统计。
```

又例如：

```text
系统观察：
第 11 小节附近长期重复出现音高不匹配。

用户反馈：
这是我正在尝试的个人改编。

系统处理：
保留原始观察，但不将其作为默认技术问题趋势。
```

用户确认的意义不能被系统扩展为更强的能力结论。对于样本不足、模式不稳定或分析可信度较低的情况，系统应优先继续观察，而不是要求用户立即解释。

---

## 3.5 证据等级、可信度与用户语义

这三个概念不是同一个维度。

### 证据等级

表示系统结论距离原始数据有多远：

```text
Fact
→ Observation
→ Candidate Trend
```

### 可信度

表示当前数据和分析是否足够可靠。它可以存在于每个证据等级中，例如：

```text
Fact：检测到一次长时间无 Note On。
可信度：高。

Observation：最近 5 次中有 3 次出现类似停顿。
可信度：中高。

Candidate Trend：该位置可能较难稳定完成。
可信度：中。
```

即使某个 Candidate Trend 的可信度很高，它也仍然是趋势解释，不应被伪装成原始事实。

### 用户语义

表示用户如何理解或处理某个观察模式：

```text
未标注
值得关注
有意行为
个人改编
自由演奏
设备或数据异常
排除在趋势之外
```

用户语义不会改变证据等级，也不会改变原始数据。

# 4. 核心概念模型

WindScore 的分析系统分为以下逻辑层：

```text
Raw Performance
+ Score Context
+ Practice Context
+ User Actions
        ↓
Observation
        ↓
Analysis
        ↓
Comparable History Set
        ↓
Candidate Trend
        ↓
User Confirmation / Correction
        ↓
User-facing Interpretation
        ↓
Optional Action
```

## 4.1 Raw Performance

尽可能保留原始数据：

- MIDI Note On；
- MIDI Note Off；
- velocity；
- channel；
- pedal events；
- 时间戳；
- 设备信息；
- MIDI 连接状态；
- 录音或回放相关信息。

---

## 4.2 Score Context

记录当前分析所对应的乐谱结构：

- 曲目 ID；
- 乐谱版本；
- 小节；
- 音符 ID；
- 音高；
- beat；
- 时值；
- 谱表；
- 声部；
- 和弦关系；
- 乐谱记号。

---

## 4.3 Practice Context

记录练习条件：

- 练习范围；
- 手部模式；
- 练习速度；
- 提示模式；
- Piano Roll / 乐谱模式；
- 是否循环；
- 是否使用节拍器；
- 是否为完整演奏；
- 是否为自由演奏；
- Attempt 类型；
- MIDI 设备。

---

## 4.4 Observation

尽可能接近原始事实，例如：

```text
根据 MIDI 记录，第 11 小节的一个预期音符未检测到对应事件。
```

而不是：

```text
用户在第 11 小节弹错了。
```

---

## 4.5 Analysis

将原始事件转换为可比较指标，例如：

- 音符匹配情况；
- 漏音次数；
- 多余音次数；
- timing deviation；
- 局部速度；
- 速度波动；
- 中断次数；
- 完成范围；
- 提示使用情况；
- 左右手同步情况。

这些指标仍然不应直接被解释为人格或能力等级。

---

## 4.6 Trend / Interpretation

结合相近条件下的历史记录，生成候选趋势：

```text
最近 5 次相近条件的练习中，
第 10–12 小节的漏音次数逐渐下降。
```

系统再根据用户反馈决定：

- 是否展示；
- 如何措辞；
- 是否纳入后续趋势；
- 是否生成复练建议。

---

# 5. 个人基线原则

WindScore 优先与用户自己的历史表现比较，而不是与其他用户或固定范本比较。

例如：

```text
用户 A：
68 BPM、71 BPM、70 BPM、72 BPM、69 BPM

用户 B：
60 BPM、105 BPM、74 BPM、120 BPM、66 BPM
```

不能仅根据速度高低判断谁表现更好。

WindScore 更关心：

- 用户是否能够持续控制自己选择的速度；
- 用户常用的速度范围；
- 用户在不同条件下的完成表现；
- 用户的中断、漏音和重试是否变化；
- 用户是否更容易完成自己想要的演奏。

基本比较关系是：

```text
当前表现
    ↕
该用户相近条件下的历史表现
```

而不是：

```text
当前表现
    ↕
固定标准演奏
```

---

# 6. 相近条件原则

不同条件下的数据不能直接混合比较。

例如：

```text
第一次：
40 BPM + 右手 + 键盘提示

第二十次：
100 BPM + 双手 + 无提示
```

不能简单说第二十次比第一次变好或变差。

趋势分析默认优先使用条件相近的历史样本。

至少记录：

```text
Score / Score Version
Practice Region
Hand Mode
Hint Mode
Tempo Range
Practice Mode
Attempt Type
MIDI Device
```

必要时记录：

```text
练习时长
距上次练习的时间
是否首次尝试
是否完整演奏
是否自由演奏
用户当前目标
```

如果没有足够相近的历史样本，系统应显示：

```text
目前条件不同，暂不直接比较。
```

---

# 7. Session、Attempt 与 Raw Performance

## 7.1 Practice Session

一次用户进入练习流程的完整会话。

例如：

```text
18:00 开始练习
        ↓
练习第 1–16 小节
        ↓
循环第 10–12 小节
        ↓
完整弹奏一次
        ↓
18:25 结束
```

这是一个 Session。

---

## 7.2 Attempt

Session 中具有独立分析意义的一次演奏尝试。

每个 Attempt 有自己的：

- 起止位置；
- 练习条件；
- MIDI 数据；
- 分析结果；
- 证据等级；
- 可信度；
- 用户反馈。

这样系统才能比较：

```text
Attempt 1 与 Attempt 2 相比发生了什么？
```

---

## 7.3 Raw Performance Data

不要只保存：

```text
节奏稳定性 = 82
```

而应保存：

```text
原始 MIDI 事件
+ 练习上下文
+ 基础事件映射
+ 分析版本
+ 计算后的统计
+ 用户反馈
```

未来算法更新后，可以使用原始数据重新计算。

---

# 8. 核心分析维度

## 8.1 音符匹配

记录：

- 预期音符；
- 实际音符；
- 匹配音符；
- 音高不匹配；
- 未检测到预期事件；
- 多余音；
- 错误位置；
- 重复出现情况。

“错音”仅表示：

> 实际 MIDI 音高与当前乐谱预期音高不一致。

它不表示：

- 用户没有音乐性；
- 用户的改编是错误的；
- 用户的表达不合格。

如果用户将其标记为改编或有意变化，该观察可以不再参与技术问题趋势。

---

## 8.2 节奏与时间变化

系统可以记录：

- onset deviation；
- inter-onset interval；
- 局部 BPM；
- timing variance；
- 长时间无事件区间；
- 连续的速度变化结构。

系统不应简单比较：

```text
是否完全跟随参考 MIDI。
```

例如：

```text
+190ms
+210ms
+180ms
+200ms
```

说明演奏整体偏慢，但相对稳定。

但是：

```text
+50ms
-300ms
+400ms
-100ms
```

表现出更明显的时间波动。

这些结果只能在练习目标和相近条件下参与趋势分析。

---

## 8.3 速度控制

记录：

- 平均 BPM；
- 中位 BPM；
- BPM 波动；
- 局部加速；
- 局部减速；
- 多次练习的速度分布；
- 用户经常主动选择的速度范围。

系统不应认为：

```text
偏离目标 BPM = 错误
```

而应区分：

```text
稳定地选择较慢速度
```

和：

```text
每次速度变化都很大
```

长期记录的是：

> 用户能够稳定控制哪些速度条件。

---

## 8.4 力度与表达相关数据

系统可以保存：

- 动态范围；
- velocity 分布；
- 左右手力度关系；
- 重复演奏中的变化；
- 踏板事件。

但基础版本不将这些自动解释为：

```text
音乐表现力提高
风格更成熟
演奏更有感情
```

除非用户明确将“力度控制”或其他表达目标设为本次练习目标，否则这些数据只作为个人演奏记录保存。

---

## 8.5 中断与连续性

记录：

- 中断；
- 长时间停顿；
- 重新开始；
- 连续完成范围；
- 从哪里开始中断；
- 从哪里重新恢复。

示例：

```text
第 14 小节附近最近出现过 4 次中断。
```

用户可以进一步标记：

```text
这是卡住了
这是有意停顿
这是设备或操作造成的异常
```

---

## 8.6 完成范围

不要只有“完成 / 未完成”。

建议区分：

```text
Reached
```

到达过某个位置；

```text
Completed
```

完整走完指定范围；

```text
Completed Under Conditions
```

在指定条件下完成，并满足当前练习目标相关的观察条件。

不使用：

```text
Clean Completed
```

因为“Clean”容易暗示只有无错误演奏才有价值。

---

## 8.7 不同提示条件下的表现

系统可以记录：

- 有提示时的完成情况；
- 无提示时的完成情况；
- 提示开启的位置；
- 提示使用频率；
- 不同模式下的错音与中断；
- 用户主动关闭提示后的表现变化。

系统不直接称其为“读谱能力分数”。

合适的表达是：

```text
最近在关闭键盘提示后，这段有更多次能够完成。
```

用户可以自行选择：

```text
继续使用提示
逐渐减少提示
只在困难位置开启提示
暂时不进行无提示测试
```

---

## 8.8 练习效率

最终版本可以记录：

- 达到某个用户目标所需的 Attempt 数；
- 达到某状态所需时间；
- 问题区域从出现到暂时不再出现所需次数；
- 间隔练习后的恢复情况。

这些数据只能描述练习过程：

```text
相同片段最近需要更少的尝试才能完成。
```

不应转化为：

```text
你的学习效率提高了。
```

除非用户明确希望关注练习效率。

---

# 9. 用户反馈系统

## 9.1 用户反馈不是附加功能

MIDI 可以告诉系统：

> 某个时间点没有检测到预期事件。

但它不知道：

- 用户是否真的卡住；
- 用户是否有意停顿；
- 用户是否在听声音；
- 用户是否正在表达；
- MIDI 是否发生异常；
- 用户是否认为这值得处理。

因此：

> **系统分析负责发现和描述长期模式，用户反馈负责在必要时补充意义。**

用户反馈不是逐条标注任务。一次练习可能产生大量停顿、未匹配音符和其他事件，系统应先自行记录、聚合和观察，不应要求用户逐一说明原因。

只有当某个模式满足以下情况之一时，才适合向用户呈现或询问：

- 在相近条件下持续出现；
- 与周围已经稳定的区域形成明显差异；
- 明显影响用户当前选择的练习目标；
- 用户主动查看该区域或希望修正系统理解。

长期稳定出现的停顿可能是有意呼吸，也可能是长期形成的犹豫、固定习惯、版本差异或对齐误差。系统可以把它识别为“稳定存在的个人模式”，但在没有其他证据时不应自动确认为主观表达或练习失误。

---

## 9.2 用户目标

用户可以选择简单的当前目标：

```text
我想顺着弹完
我想减少卡顿
我想记住音符
我想练习这个节奏
我想保持自己的速度
我想减少提示
我只是自由弹一遍
```

目标不是复杂的评分配置，而是帮助系统正确解释数据。

例如：

### 我想顺着弹完

重点关注：

- 完成范围；
- 中断；
- 重新开始。

### 我想记住音符

重点关注：

- 音高不匹配；
- 未检测到预期音符；
- 提示使用情况。

### 我想保持自己的速度

重点关注：

- 用户选择的速度；
- 速度稳定性；
- 不强行要求参考 BPM。

### 我只是自由弹一遍

本次数据可以减少或排除在技术练习趋势之外。

---

## 9.3 低频、聚合式反馈

系统默认先记录和学习，不在每次练习后追问每个事件。反馈应围绕一次练习的整体感受，或者一段时间内持续出现的少量模式。

练习结束后，可以选择性地询问一个整体问题：

```text
这次练习符合你的预期吗？

[符合]
[部分符合]
[不太符合]
[跳过]
```

当系统积累了足够历史，并发现少量稳定模式时，可以在历史视图或相关片段中询问：

```text
最近一个月，第 14 小节附近多次出现相似停顿。
这个模式对你来说是什么？

[值得继续练]
[这是有意的]
[这是我的改编]
[可能是设备或识别问题]
[暂不判断]
```

系统每次只呈现最相关的少量模式，不把数百个原始事件变成待处理列表。反馈必须可跳过；用户长期不回答时，系统继续保留中性描述，不擅自补全原因。

---

## 9.4 修正系统判断

用户可以针对一次 Attempt 或聚合后的长期模式：

- 确认某个模式值得关注；
- 忽略一次异常；
- 标记“这是有意演奏”；
- 标记“这是我的改编”；
- 标记“系统判断不准确”；
- 标记“可能是设备或数据异常”；
- 修改问题区域；
- 将一次演奏标记为自由演奏；
- 保存自己喜欢的演奏版本。

系统不能因为用户没有反馈，就自动把长期模式解释成用户意图。未确认的模式继续保持中性状态，例如：

```text
持续出现
原因未知
暂不纳入问题结论
```

用户反馈不能修改：

- 原始 MIDI 事件；
- 原始操作事件；
- 原始乐谱数据；
- 历史事实记录。

用户反馈只能修改：

- 观察的语义标记；
- 是否纳入趋势；
- 当前用户目标；
- 后续建议的解释和优先级。

---

# 10. 输出结构

## 10.1 事实层

```text
根据当前 MIDI 记录，
第 11 小节附近有 3 次未检测到预期音符。
第 14 小节附近有 2 次重新开始。
本次到达第 16 小节。
```

---

## 10.2 观察层

结合相近条件下的历史：

```text
第 11 小节附近最近比较容易出现音高不匹配。
第 14 小节附近的中断次数比之前少了。
这个片段最近三次都完成了。
```

---

## 10.3 候选趋势层

```text
在相近条件下，
第 14 小节附近可能正在变得更容易连续完成。
```

同时显示证据摘要：

```text
依据：
最近 5 次相近条件尝试；
中断次数：4 → 2 → 1；
分析可信度：中高。
```

---

## 10.4 行动层

只提供选择，不命令：

```text
[循环第 10–12 小节]
[从第 13 小节开始]
[降低速度再试]
[关闭提示测试一次]
[再完整弹一次]
[暂时忽略]
```

避免：

```text
你必须降低速度。
你应该重新学习这里。
你的节奏有问题。
```

---

# 11. 问题区域模型

问题区域不是永久标签。

不要只保存：

```text
problem = true
```

而应保存观察历史：

```text
第 10–12 小节

历史漏音观察：
5 → 3 → 2 → 1 → 0
```

问题区域应包括：

```text
起止范围
问题类型
观察次数
相近条件
证据等级
可信度
历史变化
用户反馈
是否纳入趋势
建议动作
```

状态可以是：

```text
observed
recurring
possibly_improving
temporarily_not_observed
user_marked_intentional
ignored
insufficient_evidence
```

这些状态用于描述数据，不代表用户的永久能力。

# 12. 三种练习显示模式

## 12.1 Piano Roll

适合：

- 不熟悉乐谱；
- 快速找到键位；
- 直接跟随视觉提示；
- 建立动作路径。

它不是必须被超越的阶段，而是一种合法的练习工具。

---

## 12.2 乐谱 + 键盘提示

适合：

- 建立音符与键位的映射；
- 练习读谱；
- 在困难位置获得即时辅助。

系统可以记录：

```text
在该提示条件下完成了什么。
```

但不评价用户是否“依赖提示”。

---

## 12.3 纯乐谱

适合：

- 独立定位音符；
- 连续完成片段；
- 检查减少提示后的表现。

系统可以展示不同条件下的表现变化，但不要求所有用户都必须达到无提示状态。

# 14. 从 MVP 到最终版本

## Phase 1：可靠记录

实现：

```text
乐谱稳定 ID
MIDI 原始数据保存
练习范围记录
Attempt 切分
速度和提示状态记录
原始数据回放
证据来源记录
```

目标：

> 系统准确知道用户练了什么。

---

## Phase 2：发现卡点

实现：

```text
基础乐谱 / MIDI 对齐
音高不匹配
未检测到预期音符
多余音
明显中断
问题区域聚合
用户确认和忽略
一键循环复练
```

目标：

> 系统指出的位置，用户认为有帮助。

---

## Phase 3：看见变化

实现：

```text
相近条件筛选
重复观察统计
完成范围变化
中断次数变化
音高匹配观察变化
不同提示条件下的表现
个人速度范围
证据摘要
```

示例：

```text
最近 5 次相近条件的尝试中，
第 10–12 小节的中断次数从 4 次减少到 1 次。
这说明该位置可能正在变得更容易连续完成。
```

目标：

> 用户可以看见自己原本感觉不到的变化。

---

## Phase 4：个人练习仪表盘

实现：

```text
每首曲子的练习历史
片段卡点地图
最近变顺的片段

个人常用速度范围

不同提示条件下的完成表现
用户自定义目标
用户收藏的演奏版本
```

目标：

> 系统理解用户自己的练习轨迹，而不是把用户放入统一等级。

---

## Phase 5：个人演奏版本

实现：

```text
同一曲目保存多个用户版本
比较用户自己的不同演奏
记录个人速度偏好
记录个人力度与踏板习惯
允许用户标记喜欢的版本
支持自由速度和个性化表达
```

目标：

> 帮助用户更好地控制自己想要的演奏，而不是逼近参考答案。

# 15. 最终版本功能范围

最终版本可以支持：

## 15.1 完整练习历史

用户可以查看：

- 某首曲子的全部练习历史；
- 某一片段的历史；
- 某个观察第一次出现的时间；
- 最近一次发生时间；
- 最近是否改善；
- 用户曾经如何解释该观察。

---

## 15.2 长期变化趋势

支持：

- 音符匹配观察趋势；
- 中断趋势；
- 速度稳定性趋势；
- 个人速度范围；
- 力度数据变化；
- 提示条件变化；
- 反应时间变化；
- 完成范围变化；
- 练习效率变化。

所有趋势都必须：

```text
基于相近条件
显示样本数量
显示证据等级
显示可信度
保留证据来源
```

---

## 15.3 多条件比较

可以比较：

```text
有提示 / 无提示
慢速 / 舒服速度 / 更快速度
单手 / 合手
片段练习 / 完整演奏
看谱 / 背谱
```

结果保持描述性：

> 在关闭提示后，这一段目前仍需要更多尝试。

而不是：

> 独立读谱能力不足。

---

## 15.4 个人演奏版本

同一首曲子允许用户保存多个自己的版本：

```text
Version A
Version B
Version C
```

可以比较：

- 用户选择的速度；
- 速度变化；
- 力度变化；
- 踏板行为；
- 连续性；
- 用户自己的评价。

用户可以标记：

> 这是我最喜欢的一次演奏。

系统不决定哪个版本具有更高的艺术价值。

---

## 15.5 用户自定义标准

用户可以选择自己关心的内容：

```text
我最关心连续性
我最关心少看提示
我最关心不漏音
我最关心保持自己的速度
我最关心完整弹完
我不希望系统分析力度
```

系统根据用户选择调整：

- 分析重点；
- 反馈内容；
- 趋势展示；
- 建议优先级。

# 16. LLM 的最终角色

未来可以让 LLM 负责：

- 解释练习历史；
- 回答用户关于练习数据的问题；
- 将结构化趋势转换成自然语言；
- 帮用户发现历史规律；
- 根据用户反馈调整解释方式；
- 帮助用户选择已有的针对性练习动作。

例如用户问：

> 为什么我最近感觉这首曲子顺了？

LLM 可以基于结构化证据回答：

> 最近五次相近速度的练习中，第 10–16 小节的连续完成次数增加，中断次数从平均 3 次降低到 1 次。这是一个中等可信度的改善迹象。

LLM 不负责决定：

- 用户是否有天赋；
- 哪个音一定是艺术上的错误；
- 用户是否像专业演奏家；
- 哪一种风格更高级；
- 用户是否真正“掌握”一首曲子。

LLM 是解释层，不是事实来源。

# 17. 数据可靠性与追溯原则

## 17.1 原始数据优先保存

包括：

- MIDI 原始事件；
- 乐谱版本；
- Attempt 条件；
- 用户操作；
- 用户反馈；
- 设备状态；
- 对齐结果；
- 分析版本。

---

## 17.2 分析结果带版本

例如：

```text
analysisVersion = 1
```

未来算法改变后：

```text
analysisVersion = 2
```

历史原始数据仍然保留，不能因为算法更新而永久改写过去的事实。

---

## 17.3 每条结论可追溯

系统应能回答：

```text
这条结论来自哪几次 Attempt？
对应哪些 MIDI 事件？
使用了哪个乐谱版本？
使用了哪个分析版本？
使用了哪些比较条件？
为什么被赋予这个证据等级？
用户是否确认过？
```

---

# 18. 不做什么

WindScore 不做：

```text
总分
等级排名
能力排行榜
音乐人格评分
天赋判断
专业程度判断
与大师的强制比较
强制模仿参考录音
把一次演奏变成能力结论
把用户反馈强行转成能力分数
把个人表达当成错误
把提示使用本身视为负面
把参考 MIDI 当成唯一正确答案
```

WindScore 也不以“正确率最大化”作为唯一优化目标。

# 20. 最终产品定义

> **WindScore 不负责告诉用户“你弹得好不好”。**
>
> **WindScore 负责记录用户练了什么、在哪些条件下完成了什么、哪里曾经容易卡住、哪些控制正在变得稳定，以及用户自己认为哪些变化值得关注。**
>
> **它不是一个要求用户复制标准演奏的 AI 老师，而是一份长期的个人练习记录和反馈系统，帮助用户发现自己原本难以察觉的变化。**

WindScore 的核心原则可以浓缩为：

```text
系统负责观察
```
